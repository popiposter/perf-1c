# 1С + MS SQL Server: диагностический комплект 0.1

**Статус: пилот.** Анализатор проверен 12 автономными тестами. PowerShell-сборщик и SQL-запросы не запускались на настоящих Windows/SQL Server в среде подготовки этого комплекта. Сначала короткий запуск под наблюдением администратора; это не проверенный production-релиз.

Комплект предназначен для первого измерительного среза, а не для автоматического исправления сервера. Фактическая первопричина определяется после сопоставления с жалобой пользователя и, при необходимости, с ТЖ 1С, историей запросов и планами.

## Состав

- `Collect-OneCPerf.ps1`: локальные метрики Windows и доступные сведения SQL; создаёт ZIP и отчёт о полноте сбора.
- `sql/`: открытые SQL SELECT-запросы, которые выполняет сборщик.
- `analyze.py`: автономный расчёт приращений и HTML-отчёт; запускается на рабочем месте администратора, не требует установки Python на сервер.
- `tests/test_analyze.py`: 12 проверок расчётов/обработки неполных данных.
- `docs/case-template.md`: описание реального инцидента.
- `docs/roadmap.md`: дальнейшее развитие после первого реального измерения.
- `docs/sources.md`: первичная техническая документация.

## Предпосылки и границы

Сборщик: Windows x64, **Windows PowerShell 5.1 (`powershell.exe`, не `pwsh`)**, встроенные CIM и .NET Framework SqlClient. Ничего не загружается из интернета. Целевой SQL-профиль — SQL Server 2016 и новее; версия и права проверяются. Для старой/неопознанной версии SQL runtime-часть пропускается, а не интерпретируется как исправная. Linux-профиля пока нет.

Метрики ОС всегда относятся только к компьютеру запуска. Подключение к удалённому SQL не превращает локальные метрики Windows в метрики SQL-сервера. На разных узлах 1С и SQL запускайте сборщик отдельно с одинаковым `CaseId` в одно время. Если серверы в VM, телеметрию гипервизора и хранилища нужно добавлять отдельно.

Нужны существующая разрешённая учётная запись SQL и права чтения соответствующих DMV. Обычно для SQL Server до 2019 включительно — `VIEW SERVER STATE`, для ряда performance DMV SQL Server 2022+ — `VIEW SERVER PERFORMANCE STATE`. Это не исчерпывающий список прав для всех метаданных: для msdb, выбранной базы и части каталогов нужны отдельные разрешения. Администратор выдаёт только необходимые права. Сборщик не создаёт логины и не повышает привилегии. Если полноценного серверного разрешения нет, runtime-срез SQL намеренно пропускается, чтобы видимость только собственного сеанса не выглядела как «SQL пустой».

Для части сведений Windows нужна разрешённая административная сессия. Не отключайте корпоративные ограничения выполнения скриптов; используйте принятый в организации порядок проверки/подписания/разрешения запуска.

## Первый запуск

Распакуйте **весь** комплект, например в `C:\OneCPerfDiag`, и просмотрите исходники. Сборщик использует соседний каталог `sql`.

Откройте Windows PowerShell 5.1 на проблемном сервере. Используется Windows-аутентификация SQL текущего пользователя. Имя экземпляра должно быть тем же, которое используется для подключения в SSMS; здесь `.` — локальный экземпляр по умолчанию. `DB_NAME` замените на настоящее имя SQL-базы, не на имя информационной базы в списке 1С.

Короткая проверка получения данных:

```powershell
cd C:\OneCPerfDiag
.\Collect-OneCPerf.ps1 -SqlInstance '.' -Database 'DB_NAME' -Minutes 1 -CaseId 'case01'
```

Проверьте `coverage.html` и ошибки в `records.jsonl`. Ошибки соединения, сертификата, отсутствующих разрешений и CIM — это недостаток данных, а не отсутствие проблем производительности.

Основной срез во время замедления:

```powershell
.\Collect-OneCPerf.ps1 -SqlInstance '.' -Database 'DB_NAME' -Minutes 10 -IntervalSeconds 15 -CaseId 'case01' -IncludeMaintenance
```

Для именованного экземпляра используйте, например `-SqlInstance '.\SQLPROD'`. Это пример, не сведения о вашем сервере.

На отдельном сервере 1С, без повторного сбора SQL:

```powershell
.\Collect-OneCPerf.ps1 -SkipSql -Role onec -Minutes 10 -IntervalSeconds 15 -CaseId 'case01'
```

На SQL-узле можно указать `-Role sql`. Этот параметр только маркирует узел, а не меняет конфигурацию.

Другой локальный каталог вывода:

```powershell
.\Collect-OneCPerf.ps1 -SqlInstance '.' -Minutes 10 -OutputDirectory 'D:\DiagOutput'
```

Сборщик пишет только в собственный новый каталог. Выбирайте разрешённый том с запасом места; лучше не загружать дополнительной записью наиболее проблемное SQL-хранилище. При доступном месте менее 512 MiB сбор прекращается. По умолчанию бюджет JSONL — 128 MiB, возможен выход за границу на размер одного ограниченного результата; рядом остаются исходные файлы и создаётся ZIP.

### SQL-аутентификация

Пароль не вводится в командной строке и не сохраняется в комплекте:

```powershell
$credential = Get-Credential -Message 'SQL login for diagnostic reading'
.\Collect-OneCPerf.ps1 -SqlInstance 'SQL_HOST\INSTANCE' -Database 'DB_NAME' -SqlCredential $credential -Minutes 1
```

Соединение шифруется. Проверка сертификата включена. Если подключение не прошло из-за сертификата, предпочтительно исправить цепочку доверия/имя сервера. Для конкретного проверенного внутреннего сервера администратор может явно добавить `-TrustServerCertificate`: шифрование остаётся, но проверка подлинности сертификата отключается. Этот выбор фиксируется в манифесте. Автоматического перехода на небезопасный режим нет.

### Остановка и воздействие

`Ctrl+C` прекращает сбор; код завершения старается сохранить уже записанные данные. В случае аварийного закрытия окна остаётся записанный JSONL и первоначальный манифест, но ZIP/финальный отчёт могут не появиться.

По умолчанию одна SQL-команда имеет timeout 3 секунды, ожидание блокировки у диагностического соединения ограничено 1 секундой. После трёх последовательных ошибок источник отключается для данного запуска. Целевой шаг 15 секунд **не гарантирован**: каждый источник сохраняет свои времена начала/окончания; задержки цикла отмечаются. Это чтение с ограничениями, но не нулевая нагрузка. Если сбор заметно усугубляет ситуацию, остановите его и сохраните уже полученное.

## Что собирается

**Windows:** CPU по логическим процессорам и в целом, доступная/зафиксированная память и paging-счётчики, очередь CPU, выбранные процессы SQL/1С/IIS/PowerShell, сырые счётчики дисков, сведения об ОС/CPU/памяти/томах/службах/плане электропитания. Для запущенных процессов 1С — доступная версия исполняемого файла. Командные строки служб не собираются, так как в них могут быть секреты.

**SQL:** версия/редакция, настройки, параметры видимых баз, размещение и рост файлов, время запуска SQL, приращения ожиданий и файлового I/O, текущие запросы и сеансы с открытыми транзакциями/наблюдаемыми блокировками, очереди SQL schedulers, память процесса SQL и заявки на память для запросов. Тексты SQL, содержимое планов и пользовательских таблиц не читаются.

**Выбранная SQL-база:** размещение файлов, размер используемого журнала и состояние Query Store. Это **не** выгрузка истории Query Store.

**`-IncludeMaintenance`:** ограниченная история резервных копий за 14 дней и последние результаты SQL Agent, перечень доступных заданий без текста их шагов. Пустая история не доказывает, что копий/обслуживания нет: они могли выполняться иначе, на другой реплике или история могла быть очищена. Успешное задание также само по себе не доказывает полноту обслуживания или пригодность восстановления.

## Чего сборщик не делает

Он не запускает обслуживание/бенчмарки, не изменяет конфигурацию SQL/Windows/1С, не перестраивает индексы, не обновляет статистику, не запускает CHECKDB/SHRINK, не очищает кэш/счётчики, не завершает сеансы, не создаёт XE-сессии, не включает Query Store или ТЖ, не запускает RAS и не открывает порты. Меняются только параметры собственного SQL-соединения: NOCOUNT, DEADLOCK_PRIORITY, LOCK_TIMEOUT.

Пока нет чтения RAS/RAC, технологического журнала 1С, Windows Event Log/SQL Errorlog, фактических/кэшированных планов, runtime-истории Query Store, антивирусной конфигурации, глубокой статистики/индексов, метрик гипервизора/хранилища. Поэтому по этому комплекту нельзя обещать установление любой первопричины или точное сопоставление SQL-запроса пользователю 1С.

## Результат

В `output\case01_ИМЯСЕРВЕРА_...` появятся:

- `manifest.json`: параметры, узел, время UTC и часовой пояс, границы возможностей.
- `records.jsonl`: построчные результаты каждого источника с временем, статусом и данными.
- `coverage.json` и `coverage.html`: что удалось/не удалось собрать.
- рядом с каталогом — ZIP с результатом.

**Конфиденциальность:** ZIP не обезличен и не зашифрован. Имена серверов, баз, путей, заданий и сведения о запросах/сеансах являются внутренними данными. Перед передачей наружу проверьте архив. Не добавляйте пароли или строки подключения с паролями в описание инцидента. Отсутствие SQL-текста не превращает архив в публичный. Автоматической отправки куда-либо нет.

Вместе с результатом заполните `docs/case-template.md`: что тормозило, когда (с часовым поясом), ожидаемая и реальная длительность, узлы 1С/SQL, сколько пользователей затронуто. Сделайте второй срез в нормальный период с теми же параметрами, если такой период есть.

## Автономный анализ на рабочем компьютере

На сервере Python не нужен. На рабочем компьютере администратора требуется Python 3.10+ без дополнительных пакетов:

```powershell
python .\analyze.py 'C:\Captures\case01_SQLHOST_....zip' --output 'C:\Captures\analysis-case01'
```

Откройте `report.html`. В `summary.json` находятся расчёты в машиночитаемом виде. Исходные данные не изменяются. Входной ZIP читается в памяти без распаковки произвольных путей.

Отчёт вычисляет прирост ожиданий и взвешенную задержку файлового I/O только между пригодными соседними снимками. При перезапуске SQL, обнаруженном уменьшении счётчика, смене идентичности файла или пропуске снимка соответствующие интервалы не используются. Ноль операций = нет измерения задержки, а не 0 мс. Суммарное время ожиданий может превышать длительность наблюдения из-за параллельных работников. Фоновые ожидания скрыты только в представлении, исходные данные сохранены.

Периодические снимки пропускают короткие запросы/блокировки. Значения CPU/elapsed/reads активных запросов нельзя просто складывать между снимками. Анализатор этого не делает. Полноценного сравнения двух инцидентов и объединения нескольких хостов пока нет; они предусмотрены следующим этапом.

## Проверки

```powershell
python -m unittest discover -s tests -v
```

Проверены 12 тестов анализатора, включая взвешенные задержки, отсутствие операций, сброс ожиданий, смену файла/эпохи SQL, отсутствие разрешённых данных, отрицательный ID блокировщика и экранирование HTML. Эти тесты не заменяют интеграционную проверку PowerShell/CIM/SQL на целевом сервере.
