# Настройки SQL и обслуживание

Версия анализатора 0.3.0-pilot. Сборщик остаётся 0.1.3-pilot; SQL-файлы аудита дополнены.
Не считать это подтверждением полной Windows/SQL совместимости. Реальные архивы не публикуются.

## Что проверяется в отчёте

`python analyze.py capture.zip --output analysis-output` формирует единый `report.html`,
`summary.json` и машиночитаемый `recommendations.json`. Новый раздел содержит правило,
область действия, текущее/предлагаемое значение, статус, условия и риски, источник с номером
строки records.jsonl и документацию. Для смены шага роста файлов формируются команда и
обратная команда. Они не выполняются. Обратная команда меняет шаг роста, не размер файла.

`review` — проверить условия перед изменением; `change` — базовая корректировка;
`keep` — пока оставить, не доказательство идеальности настройки; `unknown` — данных мало.
Рекомендация не доказывает причину текущего торможения. Точные значения 256 МиБ для ROWS
и 128 МиБ для LOG — стартовые кандидаты проекта, а не универсальные нормативы Microsoft/1С.

Правила: max worker threads, max server memory, MAXDOP/cost threshold, backup checksum/
compression, AUTO_CLOSE/SHRINK, автоматические статистики, PAGE_VERIFY, tempdb, рост файлов,
модель восстановления, CHECKDB, backup history, jobs и необходимость более глубокого аудита.
При отсутствии замеров пиков памяти не вычисляется искусственный «оптимальный процент RAM».
По CXPACKET не назначается глобальный MAXDOP=1. База в отчёте — выбранная плюс замеченные
активные базы, а не утверждение, что все базы экземпляра являются базами 1С.

## Более подробный сбор обслуживания

Используйте прежнюю команду загрузки с `-Minutes 1 -IncludeMaintenance`.
`sql/jobs.sql` теперь читает включение, последнее сохранённое выполнение каждого задания,
расписания, признаки операций в шагах, связь с SSIS maintenance plan и наличие оператора
для email. Сырые команды шагов, пароли, сообщения выполнения и адреса email не выгружаются.
Признаки BACKUP/CHECKDB/STATISTICS/INDEX/SHRINK — только лексические подсказки; комментарии,
обёртки и SSIS не дают этим способом точного доказательства исполняемых действий или баз.

Для полноты чтения Agent нужны sysadmin ИЛИ роль SQLAgentReaderRole/SQLAgentOperatorRole
в msdb. Ограниченная видимость SQLAgentUserRole не выдаётся за список всех заданий.
Права инструмент не выдаёт. TOP 201 согласован с лимитом сборщика 200; вложенные списки
ограничены 50 шагами/расписаниями с отдельными полными счётчиками. Усечение означает пробел.
Сохранённый next_run_time может обновляться с задержкой; отсутствие расписания не исключает
ручной/внешний запуск. Наличие расписания не подтверждает его успешную работу.

`sql/databases.sql` добавляет LastGoodCheckDbTime. NULL/сентинел/недостаточные права —
неизвестно; отметка не заменяет проверку характера CHECKDB и восстановление резервной копии.
Backup history по-прежнему ограничена 14 днями и выбранной базой, не всей инфраструктурой.
Старые архивы поддерживаются: отсутствующие новые поля становятся «неизвестно», не «нет планов».

## Генератор и установка SQL Agent jobs

`New-OneCMaintenance.ps1` — самодостаточный PS7 сценарий. Не требует Python, SqlServer module,
Ola Hallengren, SSIS или скачивания зависимостей. Это T-SQL jobs в SQL Server Agent → Jobs,
а не графические SSIS-планы в узле Maintenance Plans. Для полноценного обслуживания SSIS не обязателен.

По умолчанию создаются только ЛОКАЛЬНЫЕ файлы. Подключения к SQL нет.

```powershell
& { $s=Join-Path $env:TEMP ('perf-maint-'+[guid]::NewGuid()+'.ps1'); Invoke-WebRequest 'https://raw.githubusercontent.com/popiposter/perf-1c/main/New-OneCMaintenance.ps1' -OutFile $s -ErrorAction Stop; & $s -Database 'DB_NAME' }
```

Путь к существующему каталогу копий запросится интерактивно; это путь, видимый СЛУЖБЕ SQL,
не компьютеру администратора. Не указывайте путь к рабочим MDF/LDF. Для запуска без вопросов:

```powershell
.\New-OneCMaintenance.ps1 -Database 'DB_NAME' -BackupDirectory 'D:\SQLBackups' -NonInteractive
```

`D:\SQLBackups` — пример, не обнаруженный том. Физическая независимость от диска базы,
запас места, права службы SQL и внешняя копия проверяются оператором. Каталог не создаётся
на SQL-сервере автоматически и доступ не выдаётся.

Пакет содержит:
- `install.sql`: транзакционная установка отключённых заданий, существующие чужие/изменённые
  задания не перезаписываются; идентичные сохраняются. Проверяются описание, шаг и расписание.
- `enable.sql`: отдельное включение; `@Approved=0` блокирует выполнение до ручного согласования.
  Для FULL/BULK_LOGGED без управляемых LOG jobs нужно отдельно подтвердить внешние LOG backups.
- `disable.sql`: выключить расписанные задания пакета. Уже выполняющееся задание не останавливается.
- `remove.sql`: удалить только задания с совпадающей сигнатурой пакета; запущенные не удаляются.
  Это удаление управляемых объектов, не восстановление произвольных старых планов.
- `package.json`: параметры, задания, оговорки и результат Apply, без учётных данных.

`-Apply` после ShouldProcess-подтверждения выполняет только install.sql. Новые задания
отключены, сохранённые существующие не меняют enabled. SQL/sysadmin требуется именно
оператору установки, не всем диагностическим сборам. `-WhatIf` готовит локальные файлы,
но не подключается к SQL. Шифрование включено; `-TrustServerCertificate` только явно,
политики выполнения и HTTPS не меняются.

## Стартовый профиль расписания (предложение, не универсальная норма)

| Операция | По умолчанию | Ограничения |
|---|---|---|
| FULL backup + VERIFYONLY | Ежедневно 01:00 | CHECKSUM, COMPRESSION, уникальное имя. Обычная full copy, не COPY_ONLY: влияет на differential base |
| Обновление статистик | Ежедневно 03:00 | sp_updatestats, default sampling; для disk-based таблиц учитываются изменения. Не FULLSCAN всех таблиц |
| Полный CHECKDB | Воскресенье 04:00 | MAXDOP=2; без REPAIR и TABLOCK; нужен запас места для snapshot и tempdb |
| LOG backups | Только с -LogBackupMinutes 15 | Только FULL/BULK_LOGGED; recovery model не переключается |

Часы — локальное время SQL Agent. Параметры: FullBackupTime, StatisticsTime, CheckDbTime,
CheckDbDay, LogBackupMinutes; базы задаются явно (1–20), системные запрещены для этого профиля.
Нельзя назначать один тяжёлый профиль всем базам экземпляра без оценки нагрузки.
STATS/CHECKDB используют общий applock в master: тяжёлые задания пакета не выполняются
одновременно. При занятости задание получает ошибку и до двух повторов с интервалом 5 минут,
а не ложный успех. LOG не ждёт этот lock. Backup I/O может пересекаться с тяжёлыми работами.
Жёсткого ограничения длительности одной операции пока нет; расписания необходимо разнести
по реальным длительностям. Этот пакет рассчитан на standalone SQL, не AG/log shipping.

### Что обязательно доделать до производственного включения

1. Определить RPO/RTO, список баз и единственного владельца backup policy. Проверить существующие
   агенты/SSIS/внешние backup systems, чтобы не дублировать и не менять чужую differential base.
2. Подготовить хранилище, расчёт объёма и цепочко-зависимую retention policy. Пакет НИЧЕГО не
   удаляет: автоматическая очистка по расширению/возрасту опасна для цепочек. Контроль свободного
   места и перенос/репликация копий вне сервера обязательны как отдельные эксплуатационные задачи.
3. Настроить уведомления. `-OperatorName` использует существующего включённого email-оператора
   и уведомление об ошибке; Database Mail и профиль SQL Agent этим пакетом не настраиваются.
   Без OperatorName нужен другой согласованный мониторинг. Проверьте доставку тестовой ошибки.
4. После установки отключённых jobs сделать контролируемый первый FULL backup через Agent,
   проверить Job History, реальное восстановление в отдельную базу и CHECKDB восстановленной копии.
   Для FULL-модели подтвердить начало backup chain перед регулярными LOG jobs.
5. Только затем согласовать и выполнить enable.sql. Следующим диагностическим сбором проверить
   расписания, результаты, отсутствие конфликтов и достаточный запас места.

VERIFYONLY не заменяет реальное восстановление. Полные копии системных master/model/msdb,
backup retention, внешнее хранилище и restore-test — не реализованы этим генератором.
Обслуживание индексов по умолчанию не создаётся: нужны адресные измерения плотности/
фрагментации и реального выигрыша. Нельзя делать «nightly REBUILD ALL + FULLSCAN ALL».
Офлайн REBUILD в Standard может блокировать пользователей; REORGANIZE не обновляет статистики.

## Проверки разработки

Python: целевые тесты рекомендаций плюс регрессии существующего анализатора.
`pwsh -NoProfile -File .\tests\Test-Maintenance.ps1` проверяет синтаксис, генерацию,
экранирование имён, preview/WhatIf без SQL. В текущей среде PS7 отсутствует — этот тест
добавлен, но НЕ выполнен. Новые запросы аудита и установка jobs НЕ проверены на SQL Server.
Перед Apply сначала выполнить PS-тест и просмотреть сгенерированный SQL; испытать пакет
на отдельном тестовом экземпляре. Успех Python-тестов не доказывает корректность SQL/PS.
