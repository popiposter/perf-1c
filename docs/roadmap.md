# Дальнейшее развитие от реального инцидента

## Сначала подтвердить надёжность первого среза

Пилот на Windows/SQL; уточнить версии и топологию; проверить права, ошибки и полноту, сопоставить время с жалобой. Поправлять только проявившиеся проблемы совместимости, не строить инфраструктуру ради инфраструктуры. Интеграционные проверки: локальный/удалённый/именованный SQL, SQL 2016/2019/2022+, Windows/SQL auth, нехватка прав, сертификат, два сервера, перезапуск SQL, переполнение вывода, остановка. Замерить реальную нагрузку сборщика.

## Точечные дополнительные источники

RAS/RAC: только чтение доступных свойств кластера/рабочих процессов/сеансов; отдельные права, никаких административных изменений. ТЖ 1С: сначала импорт существующего журнала; временный фильтр логирования — отдельная подтверждаемая операция с резервной копией logcfg.xml, лимитом места, сроком и восстановлением. Конкретные события/поля/единицы длительности сверять по установленной версии платформы. Связь сеанс 1С → rphost → SQL только при наличии подтверждающих идентификаторов и времени; не обещать 1:1 при пуле соединений.

Query Store: читать историю лишь при её наличии и исправном состоянии; включение/изменение режима отдельно. XE: предпочтительно читать имеющиеся данные; узкая временная сессия отдельно от read-only-профиля. План выполнения/SQL-текст — по выбранному запросу, с контролем чувствительных значений.

Ошибки Windows/SQL, антивирус и сторонние процессы, сеть между клиентом/1С/SQL, гипервизор и хранилище. Для SQL HA учитывать, с какой реплики/узла снимались метрики и выполнялись бэкапы.

Обслуживание: фактическая история выполнения и пересечения с жалобой, свойства статистик конкретных горячих таблиц, sampling/изменения, плотность страниц/фрагментация только по выбранным объектам, подтверждённые проверки целостности и восстановления. Не сканировать все индексы большой базы в DETAILED автоматически.

## Анализ и интерфейс

Один локальный интерфейс: импорт архива → проблемный интервал → наиболее вероятные причины → доказательства → что ещё нужно измерить → безопасный план изменений → сравнение до/после. До этого достаточно статического HTML и CLI.

Версионируемые правила; статусы «факт / гипотеза / не хватает данных». Для каждой рекомендации: источник, измерение, интервал, область действия (хост/экземпляр/база/сеанс), уверенность, риск и способ проверки. Не выводить «всё хорошо» при неполном сборе.

Хранение: исходный ZIP + нормализованный JSON; позднее локальный SQLite/DuckDB по реальным объёмам. Не нужны обязательные Docker, Redis, брокер, отдельная серверная БД или облако. LLM необязательна, не источник измерений, не получает необезличенные журналы автоматически и не исполняет исправления.

## Проверка эффекта

Выбрать повторяемую пользовательскую операцию и исходный результат. Одна обоснованная корректировка за раз, с подтверждением и откатом. Повторить измерение при сопоставимом числе пользователей, параметрах и состоянии кэшей. Сравнить длительность операции, throughput, ресурсы, ожидания, блокировки, фоновые задания и побочные эффекты. Улучшение одного показателя не равно устранению причины.
