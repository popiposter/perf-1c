# SQL Maintenance Advisor: индексы и статистики

Анализатор **0.4.0-pilot**, отдельный аудит и генератор индексов **0.1.0-pilot**.
Это дополнительный профиль: обычный Collect-OneCPerf.ps1 не начинает сканировать индексы.
На сервере разработкой ничего не применено. Новые PowerShell/SQL пути требуют пилота на Windows/SQL.

## Три отдельные операции

1. `Start-OneCPerf.ps1 -IndexAudit` → read-only аудит одной явно выбранной базы.
2. `python analyze.py index_*.zip --output analysis-output` → HTML и JSON с рекомендациями.
3. `New-OneCIndexMaintenance.ps1` → локальный пакет; `-Apply` отдельно устанавливает ОТКЛЮЧЁННЫЕ задания.

Никаких автоматических SQL исправлений по результатам сканирования. Создание заданий не включает
и не запускает их. Пакет не создаёт индексы в таблицах 1С, не изменяет FILLFACTOR, настройки
параллелизма экземпляра или модель восстановления и не выполняет SHRINK.

## Аудит одной командой в PS7

```powershell
& { $s=Join-Path $env:TEMP ('perf-1c-'+[guid]::NewGuid()+'.ps1'); Invoke-WebRequest 'https://raw.githubusercontent.com/popiposter/perf-1c/main/Start-OneCPerf.ps1' -OutFile $s -ErrorAction Stop; & $s -IndexAudit -SqlInstance 'SQL_HOST' -Database 'DB_NAME' -NonInteractive }
```

SQL_HOST/DB_NAME — примеры. Для воспроизводимого запуска замените main в URL и `-Ref` одним
проверенным commit SHA. HTTPS и ExecutionPolicy не ослабляются. `-TrustServerCertificate`
допустим только явно для проверенного SQL-узла: шифрование остаётся, проверка подлинности
сертификатом пропускается. Аутентификация Windows; SqlCredential передаётся объектом PSCredential.

Результат: отдельный `index_*.zip` под `%LOCALAPPDATA%\perf-1c\captures`, `manifest.json`,
`records.jsonl`, `coverage.json/html`. Имена баз/таблиц/индексов конфиденциальны. Никаких
гистограмм, filter_definition, значений параметров или пользовательских строк; автоматической отправки нет.

### Ограничение нагрузки и охвата

| Параметр загрузчика | По умолчанию | Смысл |
|---|---:|---|
| IndexAuditMaxIndexes | 30 | Максимум физических измерений секций rowstore индексов; диапазон 1–200 |
| IndexAuditMinPages | 1000 | Нижняя граница leaf-страниц кандидата |
| IndexAuditMaxStatistics | 1000 | Максимум объектов статистик; диапазон 1–5000 |
| IndexAuditBudgetSeconds | 60 | Мягкий бюджет всего аудита; 1–900 секунд |
| QueryTimeoutSeconds | 3 | Таймаут каждого SQL-запроса; 1–15 секунд |
| IndexAuditObjectId | 0 | 0 — выбранная база, положительный ID — конкретная таблица |
| IndexAuditScanMode | LIMITED | SAMPLED разрешён только с явным положительным object_id |

Это не гарантированное время возврата: бюджет не начинает следующий запрос после истечения,
но уже начатый запрос, отмена и освобождение ресурсов могут занять больше времени. Максимум
вывода 32 МиБ; свободное место перед стартом не менее 512 МиБ. После трёх последовательных
ошибок физическое сканирование прекращается. Не пытайтесь диагностировать загруженную базу
DETAILED-сканом всех объектов. Даже LIMITED берёт IS-lock и создаёт I/O.

Сначала собираются метаданные статистик, heaps и история собственных заданий, затем до
30 крупнейших подходящих секций rowstore. **Это не топ наиболее фрагментированных объектов**:
фрагментация до физического измерения ещё неизвестна. Полный счётчик кандидатов, лимиты,
ошибки, `truncated`, `partial` и достигнутый бюджет сохраняются. При лимите статистики выбираются
по object_id/stats_id, не по степени устаревания. Измерения секций не складываются как индексы.

Режим `LIMITED` не измеряет плотность leaf-страниц: `NULL` остаётся «не измерено». Для конкретной
таблицы можно отдельно выбрать SAMPLED; для небольшого индекса SQL может фактически выполнить
полный скан. Это не фоновой мониторинг и не «бесплатная» операция. Первую проверку делать в тихий период.

### Версии и права

Windows x64 PS7, SQL Server 2016+. Аудит требует полного просмотра метаданных базы:
VIEW DEFINITION и соответствующие права DMV (до 2022 — VIEW DATABASE STATE;
с 2022 — VIEW DATABASE PERFORMANCE STATE и VIEW SECURITY DEFINITION). Инструмент
права не выдаёт. Для отдельных свойств статистики нужны дополнительные разрешения
на соответствующие объекты: недоступные свойства сохраняются через OUTER APPLY как unknown,
а не исчезают. История собственных заданий читается из msdb отдельно; её ошибка не стирает
успешные физические измерения. Выбранный object_id проверяется до начала скана.

AG-базы исключены из этого профиля, чтобы не запускать physical_stats на readable secondary
и не мешать REDO. Установщик также исключает log shipping. Нет поддержки columnstore,
XML/spatial, memory-optimized индексов и indexed views. Heaps здесь проверяются только
по метаданным размера, без физического сканирования и без автоматического создания clustered index.

## Как строятся рекомендации

Для измеренного поддерживаемого индекса/секции:

| Политика по умолчанию | Вывод |
|---|---|
| Менее 1000 страниц или фрагментация <5% | Не обслуживать по выбранному порогу; не объявлять сервер исправным |
| 5% ≤ фрагментация <30% | Кандидат REORGANIZE, если ALLOW_PAGE_LOCKS=ON |
| Фрагментация ≥30% | Кандидат REBUILD с оценкой пользы и окна; это не автоматическое разрешение |
| Ошибка, неподдерживаемый тип, отсутствующие значения | Unknown, без команды изменения |

**5/30% и 1000 страниц — настраиваемая эвристика проекта, не универсальная современная норма
Microsoft или 1С.** API `recommend_indexes` принимает другую политику; генератор имеет параметры
MinPages/ReorganizePercent/RebuildPercent. В отчёте выводится реально использованная политика
советчика (порог сканирования и порог рекомендации — разные параметры).

Плотность страниц показана отдельно, если измерена. Нужны связь с диапазонными сканированиями,
характеристики хранилища и сравнение производительности до/после. SQL-команды в отчёте —
образцы только для ручного согласования; имена экранированы, секция указывается адресно.
Для непартиционированного индекса PARTITION не добавляется. У физического обслуживания нет
простой обратной команды, возвращающей прежнюю структуру/планы.

Статистики оцениваются по доступности свойств, изменениям ведущего столбца, числу строк
и выборке. Начальная эвристика — не менее 500 изменений и не менее 20% от unfiltered_rows
при последнем обновлении; это НЕ алгоритм auto-update SQL. Низкая выборка, старая дата
или NULL даты сами по себе не означают устаревание. NORECOMPUTE и incremental требуют
отдельного разбора; глобальный FULLSCAN не предлагается. Изменения ведущего столбца не равны
точному количеству уникальных изменённых строк.

REORGANIZE не обновляет статистику. Обычный непартиционированный REBUILD обновляет статистику
самого индекса, но не все отдельные статистики столбцов; у секционных/resumable операций
есть особенности выборки. После каждого REBUILD не добавляется UPDATE STATISTICS ALL.
Базовый отдельный STATS-job из New-OneCMaintenance остаётся отдельной согласуемой политикой.

Для старых архивов появляется «индексы/статистики не измерены», а не выдуманное число
фрагментированных объектов. Имена физических таблиц SQL не заменяются именами документов
и регистров 1С без настоящей карты метаданных.

## Подготовка INDEX jobs

```powershell
& { $s=Join-Path $env:TEMP ('perf-index-maint-'+[guid]::NewGuid()+'.ps1'); Invoke-WebRequest 'https://raw.githubusercontent.com/popiposter/perf-1c/main/New-OneCIndexMaintenance.ps1' -OutFile $s -ErrorAction Stop; & $s -Database 'DB_NAME' }
```

По умолчанию только локальные файлы, без SQL-соединения. Можно явно передать массив 1–20 баз.
Каталог `%LOCALAPPDATA%\perf-1c\maintenance\index_package_*` содержит install.sql, enable.sql,
disable.sql, remove.sql и package.json. Отдельный SQL Agent job на базу: `perf-1c-<hash>-INDEX`.
Не графический SSIS-план; прежние FULL/LOG/STATS/CHECKDB jobs не заменяются.

Стартовое расписание: воскресенье 05:00, локальное время SQL Agent. Меняется параметрами
MaintenanceDay/MaintenanceTime. Это предложение, а не гарантия свободного окна после CHECKDB.

По умолчанию в работе: до 50 секций за запуск, min_pages=1000, пороги 5/30, MAXDOP=2 для
REBUILD, LOCK_TIMEOUT=5 секунд, мягкий бюджет 30 минут. Список ротируется по старейшей записи
проверки собственного журнала, чтобы крупнейшие индексы не вытесняли остальные бесконечно.
Есть статусы completed_subset, no_action_by_policy, offline_not_approved, page_locks_disabled,
budget_stop, error и succeeded. **Успешная обработка подмножества не означает обслуживание всей базы.**

Кандидаты REBUILD по умолчанию откладываются. Для их разрешения в пакет необходимо явно
передать `-AllowOfflineRebuild`. Это разрешает **OFFLINE** rebuild, который может блокировать
пользователей всё время операции, включая Enterprise. Online/resumable пока не реализованы.
Никакого автоматического fallback ONLINE→OFFLINE. SORT_IN_TEMPDB по умолчанию OFF, ON —
только при явных SortInTempdb + AllowOfflineRebuild. FILLFACTOR сохраняется; у REORGANIZE
явно отключено дополнительное LOB_COMPACTION, обслуживание LOB требует отдельной оценки.

Общий session applock `perf-1c:heavy-maintenance` в master согласован с базовым генератором:
INDEX не пересекается со STATS/CHECKDB perf-1c. Он не блокирует внешние задания и backup I/O.
При занятом lock задание завершается ошибкой без запуска работ. После трёх ошибок объектов
цикл прекращается; ошибки/отложенные операции и исчерпание бюджета отражаются как требующие
внимания, а не успешное полное обслуживание. Уже начатую операцию бюджет не прерывает.

### Установка и включение — отдельно

Сначала запустить `tests/Test-IndexMaintenance.ps1`, проверить SQL и испытать пакет
на отдельном тестовом экземпляре. `-Apply` вызывает ShouldProcess и исполняет только install.sql;
новые задания отключены. `-Apply -WhatIf` создаёт файлы, но не подключается. Требуется
авторизованный SQL sysadmin; установка не выдаёт прав. Шифрование включено, проверка
сертификата отключается только явным параметром оператора.

Установка транзакционная: существующие задания с тем же описанием, командой и расписанием
сохраняются; отличающиеся не перезаписываются. Текущее enabled существующего совпадающего
задания сохраняется. Для смены политики нужно сначала отдельно просмотреть/удалить старый
принадлежащий пакету job, а не перезаписывать чужие шаги. enable.sql требует ручного @Approved=1.
Перед включением: рабочие резервные копии и restore-test, место для второго индекса/журнала,
окно, проверка внешнего обслуживания, уведомления и длительности. OperatorName использует
существующего включённого оператора; Database Mail и проверка доставки остаются отдельными.

Устанавливается собственная таблица истории `msdb.dbo.perf1c_IndexMaintenanceLog_v1` с меткой
владельца; пользовательская схема 1С не изменяется. В историю записываются база/объект/секция,
измерение до операции, действие, время, результат и ошибка. Наличие последнего succeeded
не доказывает текущее физическое состояние: следующий аудит измеряет его снова. last_updated
статистики НЕ используется как дата дефрагментации.

Журнал не удаляется автоматически: нужно согласовать его хранение и контроль размера msdb.
disable.sql запрещает будущие запуски, но не останавливает уже выполняющееся задание.
remove.sql проверяет принадлежность/содержимое и отсутствие текущего запуска, удаляет только
job и его неиспользуемое расписание; общий журнал сохраняется. Это не rollback выполненного REBUILD.

## Проверки и границы текущей поставки

```powershell
python -m unittest discover -s tests -v
pwsh -NoProfile -File .\tests\Test-IndexMaintenance.ps1
```

В среде этой доработки выполнены 12 исходных тестов интервалов и 37 новых целевых тестов:
30 — рекомендации/HTML/интеграция/ZIP, 7 — статические контракты SQL/PS исходников.
Обычный ранее полученный архив обработан локально без копирования его данных в Git.
Это не полный повтор всех прежних тестов проекта. PS7/Windows/SQL здесь отсутствуют:
PowerShell-тест добавлен, но НЕ выполнен; T-SQL/установка jobs не проверены на SQL Server.
Статические проверки не подменяют парсер PowerShell или runtime SQL. CI не включался.
