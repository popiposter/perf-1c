# perf-1c

Локальный инструментарий диагностики производительности **1С + Microsoft SQL Server**.

Цель: связать конкретное замедление пользователя с измерениями Windows, SQL Server и 1С; отделить факты от гипотез и проверить эффект изменений.

**Текущая версия: 0.1.0-pilot.** Стартовый комплект импортируется из `onec-sql-diagnostics-v0.1`. Анализатор имеет 12 автономных тестов. PowerShell-сборщик и SQL-запросы ещё не проверены на реальном Windows/SQL Server. Это не готовый production-релиз и не автоматический оптимизатор.

## Начало работы

Полные требования, разрешения, ограничения и команды: [README_RU.md](README_RU.md).

Сначала короткий запуск в Windows PowerShell 5.1 x64 под наблюдением администратора:

```powershell
.\Collect-OneCPerf.ps1 -SqlInstance '.' -Database 'DB_NAME' -Minutes 1 -CaseId 'case01'
```

`.` и `DB_NAME` — примеры, а не параметры проблемного сервера. Перед запуском прочитайте инструкцию. Метрики Windows относятся только к узлу запуска; отдельные серверы 1С и SQL требуют отдельных сборов.

## Структура

- `Collect-OneCPerf.ps1` и `sql/` — ограниченный сбор диагностических данных.
- `analyze.py` и `tests/` — автономный анализ и тесты.
- `docs/case-template.md` — карточка реального инцидента.
- `docs/roadmap.md` — план развития после первого измерения.
- `docs/sources.md` — технические источники исходного комплекта.
- `AGENTS.md` — правила для разработки и агентов.
- `SHA256SUMS.txt` — контрольные суммы исходного импорта 0.1; это не манифест будущих изменений.

## Локальные тесты

Python 3.10+, без сторонних зависимостей:

```bash
python -m unittest discover -s tests -v
```

Успех этих тестов не подтверждает работоспособность сборщика на Windows или совместимость SQL-запросов с конкретным сервером. CI в стартовом импорте не включён.

## Диагностические данные

В Git хранятся код, документация и синтетические тесты. **Не коммитьте реальные замеры, технологические журналы, SQL-планы, резервные копии, пароли и сведения заказчика.** Каталоги вывода и типовые чувствительные артефакты исключены через `.gitignore`, но это не заменяет проверку содержимого перед коммитом.

Рабочий цикл: сбор → проверка полноты → наблюдения и гипотезы → точечная диагностика → согласованное изменение → сравнение до/после.
